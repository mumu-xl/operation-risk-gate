# 风险判定策略

## 判定标准

当操作属于高风险、实际影响不清楚、目标未解析，或安全性依赖未经验证的假设时，必须返回 `REQUIRE_CONFIRMATION`。只有当操作范围明确且不存在造成严重或不可逆损害的可信路径时，才可以直接返回 `ALLOW`。用户在审查前表达的授权不能替代风险披露后的二次确认。

## 一律要求二次确认的高风险操作

- 破坏性数据库操作，包括删除数据库、Schema 或表，清空表，无可靠筛选条件的大范围删除，破坏性结构变更，覆盖在线数据库的恢复操作，禁用约束，以及对生产数据库执行未经审查的迁移。
- 大范围或递归删除，尤其是目标包含未解析路径、工作区根目录、用户主目录、服务器根目录、挂载卷、备份、恢复所需日志或通配符匹配结果。
- 可能丢失工作内容或改写共享历史的 Git 操作，包括强制推送、硬重置、激进清理，以及删除受保护的分支或标签。
- 修改或删除生产基础设施、命名空间、集群、存储、快照、IAM、网络防火墙、密钥、加密密钥或恢复机制。
- 执行来源未固定且未经检查的远程代码或下载内容；将网络响应直接通过管道交给 Shell；关闭安全机制；将权限提升到当前任务既定范围之外。
- 将凭据、私钥、令牌、个人信息、私有源码、数据库转储或其他敏感内容暴露给未经批准的目的地或模型。
- 具有重大影响且不可逆的外部操作，包括无边界群发、公开发布、生产部署、计费、购买、删除账号或授予权限。
- 任何在执行前无法确认目标、环境、影响范围、授权、回滚路径或数据影响的写操作。

## 范围明确时通常可以允许

- 编辑已明确限定的本地项目文件，改动可以通过差异审查，并且不包含敏感信息。
- 在当前工作区内创建新文件，且不会覆盖已有数据。
- 运行格式化、静态检查、编译和测试，且写入仅限已知的构建目录或临时目录。
- 在开发环境中应用经过审查、可以回滚、目标明确且无法连接生产环境的变更。

以上只是参考，不构成自动放行。仍需检查命令语义、解析后的路径、运行环境、权限、敏感数据、间接副作用和回滚证据。

## 审查模型的输出

门禁使用 Jev System One 的两个 `Choice` 问题：

- `decision`：在 `ALLOW` 和 `REQUIRE_CONFIRMATION` 中选择。
- `risk_level`：在 `LOW`、`MEDIUM`、`HIGH` 和 `CRITICAL` 中选择。

门禁从响应的 `answers.decision.choice` 和 `answers.risk_level.choice` 读取结果。`HIGH` 和 `CRITICAL` 必须对应 `REQUIRE_CONFIRMATION`。字段缺失、答案无效或两个答案互相矛盾，都视为审查故障；此时暂停操作，修复审查服务后重新审查。
